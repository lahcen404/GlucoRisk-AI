 # GlucoRiskAI

GlucoRiskAI is a machine-learning project for patient diabetes risk profiling. It combines clinical data preprocessing, unsupervised patient segmentation, supervised classification, model tracking with MLflow, an API for predictions, a Streamlit interface, and an Apache Airflow training workflow.

> This project is for educational and analytical purposes. Its predictions are not a medical diagnosis and must not replace advice from a qualified healthcare professional.

## Project Overview

The project follows this workflow:

1. Load the raw diabetes dataset.
2. Clean and preprocess the clinical variables.
3. Use K-Means clustering to identify patient profiles.
4. Map the clusters to project-defined `Low Risk` and `High Risk` categories.
5. Train and compare classification models.
6. Tune an SVM using cross-validation and SMOTE.
7. Register and serve the selected model through MLflow.
8. Expose predictions through FastAPI and a Streamlit application.

## Dataset

The raw dataset is stored in `data/raw/dataset-diabete.csv`. It contains 768 patient records and the following eight clinical features:

| Feature | Description |
| --- | --- |
| `Pregnancies` | Number of pregnancies |
| `Glucose` | Plasma glucose concentration |
| `BloodPressure` | Diastolic blood pressure |
| `SkinThickness` | Triceps skin fold thickness |
| `Insulin` | Two-hour serum insulin |
| `BMI` | Body mass index |
| `DiabetesPedigreeFunction` | Diabetes pedigree function |
| `Age` | Patient age |

The raw file includes an index column but does not include a target label used directly by the application. The project derives `risk_category` from K-Means cluster assignments.

## Methodology

### Preprocessing

- Treat zero values in `Glucose`, `BloodPressure`, `SkinThickness`, `Insulin`, and `BMI` as missing values.
- Standardize the clinical features.
- Impute missing values with `KNNImputer` using five neighbors.
- Inverse-transform the imputed values back to the original feature scale.
- Cap IQR-based outliers for `SkinThickness` and `Insulin`.

The processed datasets are written to `data/processed/`.

### Clustering

K-Means is evaluated for values of `k` from 2 to 10 using inertia and silhouette score. The final workflow uses `k=3` with `random_state=42` and `n_init=10`.

The project-defined mapping is:

- Cluster 1: `High Risk`
- Clusters 0 and 2: `Low Risk`

### Classification

The classification stage uses an 80/20 stratified train-test split. Each model is trained in a pipeline containing `StandardScaler` and SMOTE to address class imbalance.

The evaluated models are:

- Logistic Regression
- K-Nearest Neighbors
- Random Forest
- Support Vector Machine

The SVM is tuned with a five-fold `GridSearchCV` using F1-score for the `High Risk` class. The stored best parameters are:

```text
C=100, kernel=rbf, gamma=scale
```

## Results and Metrics

The following results are recorded in `artifacts/baseline_results.csv` on the held-out test split:

| Model | Accuracy | Precision | Recall | F1-score |
| --- | ---: | ---: | ---: | ---: |
| Logistic Regression | 85.71% | 65.52% | 95.00% | 77.55% |
| KNN | 87.66% | 69.09% | 95.00% | 80.00% |
| Random Forest | 93.51% | 82.61% | 95.00% | 88.37% |
| SVM | **94.16%** | **84.44%** | 95.00% | **89.41%** |

The final SVM is the best-performing baseline according to accuracy, precision, and F1-score. K-Means evaluation results are stored in `artifacts/kmeans_evaluation.csv`; the selected `k=3` configuration has a silhouette score of `0.2102`.

## Installation

### Requirements

- Python 3.12 or a compatible recent Python version
- Docker and Docker Compose for the complete multi-service setup

### Local Python environment

Create and activate a virtual environment, then install the dependencies:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install --upgrade pip
pip install -r requirements.txt
```

The repository expects the processed datasets and model artifacts to be available before starting the prediction API. They are generated by the project training workflow and are also represented by the files under `data/processed/`, `models/`, and `artifacts/`.

## Running with Docker Compose

Create a `.env` file in the project root. At minimum, define the variables required by Docker Compose:

```dotenv
AIRFLOW_DB_USER=airflow
AIRFLOW_DB_PASSWORD=change-me
AIRFLOW_DB_NAME=airflow
AIRFLOW__API_AUTH__JWT_SECRET=change-me-to-a-long-random-value
MLFLOW_TRACKING_URI=http://localhost:5000
MLFLOW_MODEL_NAME=GlucoRiskAI
API_URL=http://localhost:8000
```

Start the services:

```bash
docker compose up --build
```

Available services:

| Service | URL | Purpose |
| --- | --- | --- |
| Streamlit | http://localhost:8501 | Patient risk prediction interface |
| FastAPI | http://localhost:8000 | Prediction API |
| FastAPI docs | http://localhost:8000/docs | Interactive API documentation |
| MLflow | http://localhost:5000 | Experiments and model registry |
| Airflow | http://localhost:8080 | Training DAG management |

Stop the services with:

```bash
docker compose down
```

## Running Components Locally

### FastAPI

With the virtual environment active and an MLflow server available:

```bash
uvicorn api.main:app --host 0.0.0.0 --port 8000 --reload
```

Useful endpoints:

```bash
curl http://localhost:8000/health
curl http://localhost:8000/model
```

Send a prediction request with:

```bash
curl -X POST http://localhost:8000/predict \
	-H "Content-Type: application/json" \
	-d '{
		"Pregnancies": 2,
		"Glucose": 130,
		"BloodPressure": 70,
		"SkinThickness": 25,
		"Insulin": 100,
		"BMI": 30.5,
		"DiabetesPedigreeFunction": 0.5,
		"Age": 30
	}'
```

### Streamlit

Start the interface after the API is running:

```bash
API_URL=http://localhost:8000 streamlit run streamlit/app.py
```

### Training script

Start MLflow on `http://localhost:5000`, make sure the processed dataset exists, and run:

```bash
MLFLOW_TRACKING_URI=http://localhost:5000 python src/train.py
```

The script evaluates K-Means, compares the classifiers, tunes the SVM, logs the run to MLflow, and writes model and evaluation artifacts.

### Airflow training DAG

The Docker Compose Airflow service contains the DAG `glucoriskai_training_pipeline`. It performs three tasks in order:

1. Validate that `data/processed/diabetes_preprocessed.csv` exists.
2. Execute `src/train.py`.
3. Verify that `models/glucoriskai_svm_pipeline.joblib` was created.

Open Airflow at http://localhost:8080, authenticate with the credentials configured for the Airflow simple auth manager, and trigger the DAG manually because its schedule is disabled.

## Notebooks

- `notebooks/01_eda_preprocessing.ipynb`: exploratory analysis and preprocessing
- `notebooks/02_clustering.ipynb`: K-Means evaluation and patient segmentation
- `notebooks/03_classification.ipynb`: classification experiments and metrics

## Limitations

- The risk labels are project-defined cluster labels, not clinical diagnoses.
- Results depend on the preprocessing decisions, random seed, split, and generated artifacts in the repository.
- The dataset is relatively small and should not be treated as sufficient for clinical deployment.
